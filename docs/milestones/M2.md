## 3. Database migrations

| Revision | Purpose |
| --- | --- |
| `0002_identity_institution` | colleges, users, roles, user_roles, user_sessions, departments, batches, students, mentors, mentor_batch_assignments, audit_logs; reference roles |
| `0003_rls_policies` | enable/force RLS on the ten tenant tables, tenant policies, narrow `colleges` system policy, `profile_app` grants and append-only restrictions |

Both were applied to the development database (`0001` → `0003`). RLS is forced,
so the schema owner is also subject to it outside the system context.

### Tenant isolation

- `app.current_college_id` is set per transaction via `set_config(..., true)`.
- Every tenant table has `USING` and `WITH CHECK` policies against it.
- `app.is_system` widens **only** the `colleges` policy (provisioning/login).
- Composite foreign keys prevent cross-tenant references.
- `profile_app` has `SELECT, INSERT` on audit logs and no `UPDATE`/`DELETE`;
  it cannot modify the `roles` catalogue.

## 5. Authentication and session design

- Password login returns a signed JWT in the HttpOnly `pa_session` cookie
  (`SameSite=Lax`; `Secure` in production).
- The JWT carries `sub`, `col` (college) and `sid`; `sid` maps to a
  `user_sessions` row whose `token_hash` is the SHA-256 of the token.
- A token is accepted only if the signature is valid **and** the row is
  unexpired and not revoked, so logout and administrative suspension take effect
  immediately.
- Password hashes use Argon2id.
- OIDC uses a provider-agnostic adapter with state and nonce validation; an
  unknown identity is rejected rather than auto-provisioned.
- The tenant for a login is resolved from the institution code plus the
  provisioned user; a client-supplied `college_id` is never trusted.

## 7. Security considerations addressed

- Tenant identity is derived only from the authenticated session.
- RLS is forced and fails closed when no tenant context is set.
- The runtime role does not own tables and cannot bypass RLS.
- Cross-tenant reads and inserts are rejected at both the application and
  database layers.
- Mentor visibility is limited to their assigned batches; admins are limited to
  their college; only `SUPER_ADMIN` can provision colleges.
- Audit rows are append-only for the runtime role; the role catalogue is
  read-only.
- Session revocation is server-side; token reuse after logout fails.
- IP and user-agent metadata are minimized and unparseable IPs discarded.
- Tests and seeds use synthetic identities only; no real student data.

## 8. Known limitations

- No notifications yet (FR-57/FR-58 arrive with M3).
- The audit log stores a single `details` JSON document; no structured
  `before`/`after` diff yet.
- There are no frontend component tests; verification is typecheck + build plus
  manual browser checks.
- OIDC is implemented but not exercised against a real identity provider in this
  environment.
- `user_roles` still carries an `INSERT` grant from the bootstrap script; it is
  harmless (no write route uses it) but can be revoked in a later hardening
  migration.
- Super admin provisioning is minimal (create college only); richer platform
  administration belongs to later milestones.
